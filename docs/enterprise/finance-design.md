# 台灣小型店家與中小企業財務設計

文件版本：`finance-design-v1`。設計日期與官方來源查核日期：`2026-10-05`。功能狀態：`Planned`。適用初始法域：`TW`，時區：`Asia/Taipei`；法域、會計年度與政策均可設定，其他法域尚未設計完成。

本文件安排銀行統計與對帳、薪資費用、會計、報稅及電子發票的資料與操作流程。本次只交付設計，沒有新增資料表、API、畫面、銀行連線、薪轉、正式傳票、申報或發票開立能力，也沒有讀取或保存真實憑證、員工資料及銀行資料。後文所有新增按鈕、狀態、契約及檢核都是待實作項目。

## 1．現況與不可跨越的邊界

現有 `src/domain.ts` 的 `move()` 只在兩個模擬錢包間建立一負一正的 `ledger.entries`；`src/engine.ts` 驗證每筆兩腿、流水總和為零及錢包餘額守恆。它沒有會計科目、借貸方向、應收應付、傳票審核、會計期間或資產負債表，不能直接升格為總帳（GL）。現有 FIFO 出貨成本與模擬毛利也沒有包含薪資、租金、折舊、利息、稅款及其他費用。

目前工作區固定 `currency:SIM`、`simulation:true`、`real_finance:false`，命令與匯入會拒絕正式金融欄位。未來新增財務資料必須另做明確的 schema、migration、模組依賴及 validation，並驗證舊資料還原。不得把 `bank` 或 `finance` 欄位換名、藏在備註或任意 JSON，藉此繞過現有防線。

| 層次 | 資料與用途 | 外部寫入及輸出 |
| --- | --- | --- |
| 現有公開試用 | SIM、虛構商品與獨立訪客工作區 | 維持 `real_finance:false`；沒有銀行、薪轉、發票、正式報稅功能 |
| 預計本地教學 | 合成對帳單、虛構員工代碼、SIM 傳票練習、可重設的教學政策 | 僅輸出標示「模擬練習」的內部 JSON／CSV／報表；禁止轉成正式申報媒體檔或可兌獎發票 |
| 未來正式候選 | 另建受控私有實例、正式法人與授權使用者；初始本位幣候選 TWD | 未授權啟用。須通過第 12 節條件後，另訂正式實作與操作範圍 |

官方稅率、投保級距與法定期限是未來 TWD 政策的研究資料，不套入目前 SIM 金額。SIM 不能按比例換成 TWD、作為期初餘額或產生可送件的申報檔。教學政策與正式政策分庫、分版本、分輸出器；`purpose:training` 的來源不能送入 `purpose:statutory`。

## 2．模組安排與資料責任

以下七個 moduleID 全部為 `Planned`，不代表已加入目前範本或 module allowlist。

| moduleID | 預計責任 | 主要來源與交接 |
| --- | --- | --- |
| `treasury` | 銀行來源匯入、收付款、現金、票據、對帳、資金預估 | 從 AR、AP、薪資取得核准需求；把已確認清償與銀行證據交總帳 |
| `payroll` | 薪資試算、扣款、雇主負擔、薪資單及付款批次 | 只讀 HR／出勤／排班核准快照；交付應付薪資、代扣負債及雇主費用 |
| `accounting` | 科目、傳票、總帳、調整、月結與財報 | 接收經核准的業務事件；保留來源、政策與沖回鏈 |
| `tax` | 稅務分類、會稅差異、工作底稿、申報準備、回執與期限 | 讀總帳與憑證，分別管理營業稅、扣繳與營所稅，不改寫原帳 |
| `invoices` | 電子發票、字軌、作廢、折讓、存證與結果查詢 | 讀銷售事實與稅籍政策；與退貨、退款、總帳各自記錄結果 |
| `procurement` | 請購、採購、驗收、供應商帳單與差異 | PO／驗收／帳單三方核對後建立 AP；付款由 treasury 負責 |
| `assets` | 資產取得、啟用、移轉、盤點、折舊、處分 | 連結採購、費用及資產科目；帳務折舊與稅務折舊分開 |

法人（`entity_id`）是帳簿、稅籍與申報的主體；門市／部門／專案是維度。門市間轉帳不新增公司營收。不同法人不可共用科目餘額、字軌、銀行來源及申報回執。跨模組通知使用事件識別與版本，不把付款成功、帳務入帳及稅務存證壓成一個布林值。

## 3．共用資料契約

本節是未來介面草案，現有 `/commands` 與匯入格式不接受這些契約。樣本僅使用合成識別，沒有真實姓名、身分證號、帳號、載具號碼或地址。

### 3.1 共用欄位與不變條件

每個財務物件帶有 `schema_version`、`entity_id`、`workspace_id`、`purpose`、`jurisdiction`、`record_version`、`status`、`created_at`、`created_by_ref`、`source_refs[]`、`policy_snapshot_refs[]`。物件修改命令帶 `expected_version`；過時版本拒絕並提示重新預覽。ID 及來源參照不能跨法人或工作區使用。

金額使用 `Money { currency, minor, scale, money_policy_version }`；`minor` 是十進位整數字串，計算採精確十進位或整數，禁止浮點累加。原始銀行金額字串、原幣、本位幣、匯率來源／日期／版本及逐步捨入結果分開保存。不同幣別不可直接相加；財報合併須有本位幣換算與匯兌差額傳票。SIM 與 TWD 不可同帳混合。

`occurred_at` 是業務事實時間，`recorded_at` 是系統受理時間，`value_date` 是銀行起息日，`accounting_date` 是入帳日，`tax_event_date` 是依稅務政策認定的日期；各自保存，不因跨午夜或補登而覆蓋。原始時區與 UTC instant 保留，民國年度只在介面／輸出器轉換。

### 3.2 共用寫入與對外契約

本地資料修改先完成授權、用途、法人、期間、來源版本與守恆檢查，再在同一交易寫入業務資料、事件及 outbox。已核准 payload 以 hash 鎖定；尚未送出的操作若改動金額、目的地或內容，必須為新 payload 重新覆核，原核准不能套用。已核定或已執行的事實與快照保留，更正另建版本或調整事件。worker 送出前再次核對核准版與外部資格；outbox 建立只表示排隊，不表示銀行或平台已受理。

外部 connector 介面預計分 `validate`、`prepare`、`submit`、`query`、`receiveEvent`。候選銀行匯入、薪轉檔、會計師交接、申報媒體及發票 Turnkey／加值中心各有 adapter，不能以一個「通用財務 API」涵蓋。secret 只在受控執行環境以 secret reference 取得，不進文件、URL、日誌、範本或稽核 payload。

目前設計不能呼叫 `submit`。正式能力未啟用時，後端與 UI 都拒絕正式送出；隱藏按鈕不能取代後端檢核。模擬結果使用 `simulated_*`，不能產生看似官方回執、正式字軌或薪轉成功證明的附件。

## 4．銀行統計、收付款與對帳

### 4.1 來源匯入與去重

首階段只設計合成資料與 ERP 自有測試 CSV。它不是銀行通用格式。CSV／XLSX 檔名也不能證明格式；未來接入每一家銀行，須取得該銀行、產品、匯出選項與版次的官方規格，或由使用者提供且經去識別的樣本驗證，再登錄 adapter。檔案可能有不同日期曆法、編碼、小數位、借貸符號、跨列描述與「可用餘額／帳面餘額」欄位，不能自動猜完後直接入帳。

匯入流程為：選法人／帳戶 ref／期間 → 上傳受控來源 → 取得原件 hash → 選格式及 mapping 版本 → dry run → 檢查行數、幣別、期初期末、方向、錯誤與重複 → 核准批次 → 匯入隔離區 → 確認正式接收。乾跑不能新增付款、GL 或改餘額；後續原件、映射、格式或帳簿版本改變，須重新乾跑。

同帳戶、同來源 hash 的批次重複提交回原批次結果；不能因檔名變更新增資料。跨批次優先使用銀行穩定交易 ID；沒有 ID 時使用正規化指紋提出候選重複，保留原始列定位與 occurrence。兩筆同日同額可能都是合法交易，不能單憑日期＋金額自動去掉。重疊日期範圍、格式更新後重匯、來源 ID 衝突及銀行補登均需比對證據或隔離人工判定。

### 4.2 對帳配對與差異

配對建議可使用金額、參考碼、相對人內部 ref、日期範圍及業務文件，但只形成 `Proposed`。使用者能選一對一、一筆收款付多張單、多筆分次款付一張單，以及多對多的獨立分攤組。每一側都保存實際分攤，剩餘未配金額可留待下次；不得把部分付款標為整張已付。

付款額與入帳額不一致時，手續費、折扣、匯差、代扣及退款各列原因、來源與待審傳票。例如帳單價款與銀行入款扣掉手續費後不同，須能以價款清償加手續費明細核對。容差只決定是否提示，不能免去差異認列及覆核。內部銀行轉帳須同時追蹤兩側與在途款，不算銷售；貸款、業主投入、預收款、代收代付也不能因有銀行入款就認列營收。

撤銷已覆核配對建立 reversal，恢復可分攤金額並保留舊組。銀行沖正保留原交易與沖正關聯，另處理受影響收付款、AR／AP 清償與總帳調整；不得刪除歷史。已關帳期間的撤銷改走下一開放期調整，或經核准重開與重做受影響報表。

| 物件 | 狀態機 | 轉換條件 |
| --- | --- | --- |
| 匯入批次 | `Draft → DryRunPassed → PendingApproval → Imported`；錯誤到 `Quarantined`／`Rejected` | 原件、mapping、帳戶及版本一致；覆核通過後原子接收，失敗可查原批次，不部分重寫 |
| 配對組 | `Proposed → Reviewed → Confirmed → Reversed`；退回 `Rejected` | 兩側可用餘額與差異完整；制單者不能覆核自己的組 |
| 對帳期 | `Open → Reconciling → ReadyToClose → Closed`；核准後 `Reopened` | 帳簿與銀行調整後餘額一致，未達帳與爭議有清單；零差異不能跳過原件核對 |
| 收付款需求 | `Draft → Approved → Prepared → Submitted → Confirmed`；另有 `Rejected`、`Failed`、`Unknown` | 確認須有指定來源證據。手動登錄只標 `ManualEvidencePending`，不能假稱銀行已執行 |
| 票據 | `Registered → Held → Presented → Cleared`；另有 `Dishonoured`／`Cancelled` | 收到票據不等於現金入帳；到期、提示、兌現、退票分開，背書轉讓另有鏈 |

### 4.3 銀行與經營統計

頁面分別顯示銀行來源期末餘額、帳簿銀行科目餘額、調整後對帳餘額、未達帳金額、待認領款、各幣別收支與資料完整期間。沒有期初或期末來源時只能呈現交易清單，不宣稱餘額已對平。信用額度不列為現金資產；可用餘額與帳面餘額分開顯示，科目認列依帳務政策及證據。

銀行餘額不等於營收，營收不等於利潤。營收來自核准認列政策；損益另含成本及費用；現金流來自收付事實與分類。預估資金表使用 AR／AP 到期、薪資及票據，標示預計／已確認與情境假設，不能當成銀行保證餘額。應收帳齡、應付帳齡、門市收支及現金週轉可追到來源，報表必須露出快照、幣別、期間、口徑及「模擬／正式候選」標籤。

## 5．會計、採購、費用與資產

### 5.1 應收、應付與收付分離

銷售訂單、履約驗收、營收認列、AR、發票、收款及銀行確認是不同事件。認列規則由會計政策與文件事實決定，不把訂單按下付款或發票上傳成功直接當作營收。AR 保留分期、部分收款、爭議、折讓與壞帳處理；AP 保留預付、分次付款、差異與退貨。款項跨文件分攤須經核准，不可用刪單消除未清償額。

採購使用請購 → PO → 驗收／入庫 → 供應商帳單三方核對；數量、價差、稅別、重複帳單與超額請款列為例外。有驗收而無帳單的應計、已付而未履約的預付及資產取得各有過帳規則。現有 SIM `inventory.receive` 即時扣款的教學流程不代表正式採購一定即付。

費用／代墊流程為申請、附件、分類、主管與會計覆核、確認應付、付款及對帳。支出可能是費用、存貨、資產或預付款，不能全部列當期費用；收據也不能一律視為可扣抵進項。零用金另有額度、保管人 ref、補足申請與盤點，缺憑證或差額走例外。

### 5.2 總帳與月結

新 GL 另建科目與帳簿，不沿用錢包 `kind` 當正式科目。示範 posting map 只說明語意：履約時依政策「借 AR／貸收入及相關負債」，收款時「借銀行／貸 AR」，購入資產時「借資產／貸 AP」，折舊時「借折舊費用／貸累計折舊」。各筆均需合格來源、課稅分類及完整借貸平衡，不能據此自動產生正式傳票。

傳票狀態為 `Draft → Validated → PendingApproval → Approved → Posted → Reversed`。過帳後禁止修改金額、科目或來源；錯誤以沖回＋新版本處理。借貸不平、失效科目、跨法人、重複來源、關帳日期及未核准政策均拒絕。試算表平衡是必要條件，不能證明帳務分類正確或憑證完整。

月結狀態為 `Open → SoftLocked → Reviewed → Closed`。清單包括銀行及現金、AR／AP 未清項、存貨成本勾稽、應計／預付、薪資與代扣負債、資產折舊、稅務憑證、匯兌及沖回例外。每項有責任人、證據及例外核准；未確認外部操作需處理或由覆核者載明保留事項。關帳產生不可變報表快照與 hash；重開需要原因、影響範圍及另一人核准，不能偷偷修改已交給會計師的報表。

報表安排總帳明細、科目餘額、試算表、損益、資產負債、現金流、AR／AP 帳齡及來源勾稽。會計準則、法定報表、簽章／編製責任與留存期限須按公司類型另行審定。此設計不宣稱通過所有商業會計或特定產業法遵。

### 5.3 固定資產與折舊

資產流程為 `Draft → Acquired → InService → Disposed`，可另外 `Suspended`。保存取得成本組成、啟用日、資產類別、保管／門市 ref、殘值、耐用年限、折舊方法、帳務政策與稅務政策。折舊批次先預覽、覆核再過帳；同一資產同期間同政策不得重複過帳。

帳務折舊與稅務折舊各自建立 schedule，會稅差異交 tax；不得把會計耐用年限直接當稅法年限。減損、資本化後續支出、處分、報廢及出售應收款有專屬事件。取得、啟用或處分發生在月中，按政策的有效版本與按日／按月規則計算，不能事後用新政策重寫舊月。

## 6．薪資、員工扣款與雇主費用

薪資輸入使用已核准的 HR、出勤、排班及薪項快照，鎖定版本；缺勤、加班、補休、獎金、兼職、入離職、留停與補發不得靠總額推測。員工分類、投保資格、投保薪資／提繳工資、所得性質與居住者認定分開覆核，不因實領薪資較低就自動降低投保級距。

| 金額 | 定義與勾稽 |
| --- | --- |
| `gross_pay` | 應付薪資薪項總額；依法認定的薪資、投保及課稅計算基礎分開保存，三者不必相同 |
| `employee_deductions` | 員工負擔勞／就保、健保、自願提繳及其他經核准扣款分項；扣款資格與上限依有效政策 |
| `withholding` | 按所得性質、居住者分類、給付日、選用方式、累計月額及年度扣繳表計算的代扣負債 |
| `net_pay` | `gross_pay − employee_deductions − withholding`；不得把雇主負擔扣入員工實付薪資 |
| `employer_cost` | 薪資費用加雇主負擔保險、勞退、適用補充保費及其他雇主費用；付款與認列期間各自保存 |
| 報銷與薪轉總額 | 非薪資代墊報銷獨立列示，可與薪資同次付款但保留清償來源；薪轉總額不能直接當薪資費用 |

首輪只規劃虛構員工與 SIM 試算。未來正式勞保／就保、災保、健保、補充保費、勞退與扣繳規則都由年度有效版本及官方來源核對，逐員工列適用理由、級距、期間、負擔比例、捨入與來源。部分工時、不同投保資格、眷屬、職災行業費率及補發規則要有獨立分支，不能為所有小店填同一組比例。勞保局的 115 年表亦註明普通事故與就保合計表未含職災保費。[勞保局 115 年分擔表](https://www.bli.gov.tw/Files/25696)

PayrollRun 沿用[人資規格 §5.5](workforce-design.md#55-薪資與成本)的唯一狀態契約：`draft → ready → previewed → in_review → approved → released`，另有 `stale`、`voided`。核定前來源變更使可重算的草稿／待審版本轉 `stale`；`approved/released` 保留原來源、政策快照及結果，不能刷新或改寫過去薪資。發布前錯誤以核准作廢再建新版，發布後以調整批次連結原批次。只有 `released` 後才建立唯讀財務交接；發布模擬薪資單仍顯示未付款，不自動過帳、扣幣或送銀行。

Journal 的 `Posted` 表示會計過帳，不是 PayrollRun 狀態。TreasuryPayment 另有 `PaymentPrepared → Submitted → PaymentConfirmed` 與 `PaymentFailed`、`PaymentUnknown`；`PaymentConfirmed` 須有該筆付款證據，轉出薪轉檔只到 `PaymentPrepared`。尚未送出的付款 payload 改金額或目的地，僅該付款核准失效，新 payload 須重審。整批部分成功逐筆保留結果，補送僅處理可證明未執行的項目，不能整批重送。

每月可分次發薪，扣繳計算須依適用規則合併全月或分開非經常給付；不能每次從零重算。年度扣免繳憑單與給付紀錄相符；免扣繳仍可能有申報義務。薪資單列薪項、扣款、雇主費用摘要與來源版本，員工只能看自己的版本，主管看授權範圍，會計檢視負債與彙總不預設取得全部私人資料。[財政部薪資扣繳問答](https://www.etax.nat.gov.tw/etwmain/tax-info/understanding/tax-q-and-a/national/individual-income-tax/withheld-rule/rule/NM11BZY)

## 7．台灣稅務分流、政策版本與申報

### 7.1 稅籍分流

建立 `TaxpayerProfile` 時先收集受控稅籍證據，區分公司／獨資／合夥、是否小規模、主管機關核定計算方式、使用發票資格、專營或兼營、免稅／零稅率項目與特殊業別。不由店名、員工數、單月銀行入款或套用的產業範本自動推定稅籍。

| 分流 | 規劃行為 | 官方依據與限制 |
| --- | --- | --- |
| 一般稅額計算 | 銷項、可扣抵進項、不得扣抵及兼營調整各自建底稿；依期申報 | 一般稅額計算常見稅率為 5%，不代表所有營業人及所有交易都適用。[課稅方式](https://www.etax.nat.gov.tw/etwmain/tax-info/understanding/tax-saving-manual/national/business-tax/6opmkDW) |
| 查定課徵 | 管理核定銷售額、繳款書、適用扣減、異議及繳納證據 | 小規模常見 1%，另有不同業別與稅率；不能把帳簿估計取代機關核定，也不能一律產生 401。[課稅方式](https://www.etax.nat.gov.tw/etwmain/tax-info/understanding/tax-saving-manual/national/business-tax/6opmkDW) |
| 未達起徵點 | 保存核定與適用理由、監測是否需重新確認 | 114 年起相關貨物業別每月 10 萬元、勞務業別 5 萬元，兼營另有比例判斷；這不是所有小店自動免稅或免登記的門檻。[起徵點公告](https://www.etax.nat.gov.tw/etwmain/tax-info/network-transaction-taxtation-area/regulation) |
| 免稅／零稅率／兼營 | 逐明細區分稅別與證據，依核准政策處理進項與申報 | 免稅與零稅率有不同法律條件與扣抵效果；不得只把 rate 設為零。[營業稅法](https://law-out.mof.gov.tw/LawContent.aspx?id=FL006082) |
| 特種計算／其他法域 | 只建立待評估項目 | 金融、特殊飲食等不能套一般小店流程；未審定時禁止正式試算與輸出 |

營所稅再按組織分流：一般公司、獨資／合夥與經核定小規模分開。獨資／合夥非小規模仍有結算申報規定，所得額由業主／合夥人依規定列入綜所稅；小規模另有免辦結算申報規定。不能把每家小店都算成「公司利潤乘固定稅率」。業主個人綜所稅不在本輪企業資料內，僅規劃核准的交接資料。[所得稅法第 71 條](https://law-out.mof.gov.tw/LawContent.aspx?id=FL005935)、[營所稅結算申報適用對象](https://www.etax.nat.gov.tw/etwmain/tax-info/understanding/tax-q-and-a/national/profit-seeking-enterprise-income-tax/file-payment/B0zWjGa)

### 7.2 期間、基礎與期限引擎

每份底稿保存 `tax_type`、`tax_basis`、`period_id`、`calendar_version`、`policy_version`、`accounting_snapshot_hash` 及 `calculated_at`。`tax_basis` 明列認列時點、給付時點、查定或其他適用依據；營業稅、扣繳與帳務期間各自管理。營收、發票銷售額與銀行收款差異須有勾稽表，不能用一張收支表直接報所有稅。

`deadlinecalc` 以可注入 `IClock` 及法域 local date 運作：輸入已分類事件、法定規則版本、適用期間、國定假日／延期公告版本，輸出法定原期限、調整後期限、計算步驟與依據。使用者輸入日期不能改變實際 server clock；測試可固定時鐘。提醒提前量與法定期限分開。例外延長須有公告或核准證據與覆核人；手動行事曆可補充提醒，不能擅自延長法定期限。

| 稅務任務 | 正式政策研究基線，尚未啟用 |
| --- | --- |
| 一般營業稅 | 原則每二月一期，次期開始 15 日內；有無銷售額與適用例外仍須分流，月報資格另查。[營業稅法第 35 條](https://law-out.mof.gov.tw/LawContent.aspx?id=FL006082) |
| 境內居住者扣繳 | 原則次月 10 日前繳清上月扣取稅款，年度憑單原則次年 1 月底前申報；法定連續假日／特殊事件另有規定。[扣繳報繳注意事項](https://www.etax.nat.gov.tw/etwmain/tax-info/innotative-tax-e-reference/withheld/notice/qR6lGBO) |
| 非居住者扣繳 | 原則代扣日起算 10 日內繳納與申報，須使用該分流及法定假日例外；不可共用居民的次月流程。[所得稅法第 92 條](https://law-out.mof.gov.tw/LawContent.aspx?id=FL005935) |
| 營所稅結算／暫繳 | 一般曆年制結算原則次年 5 月 1 日至 31 日；另評估暫繳、特殊會計年度及決清算。暫繳免辦條件需另判。[所得稅法](https://law-out.mof.gov.tw/LawContent.aspx?id=FL005935)、[暫繳免辦條件](https://www.etax.nat.gov.tw/etwmain/tax-info/understanding/tax-q-and-a/national/profit-seeking-enterprise-income-tax/provisional-income-tax-return/EnwpQYW) |

### 7.3 申報與繳款狀態

底稿流程為 `Collecting → Validated → Reviewed → Approved → ExportPrepared`。正式未來送件流程另為 `SubmissionPrepared → Submitted → ReceiptConfirmed`，另有 `Rejected`／`Unknown`；稅款為 `NotDue`／`Due`／`PaymentPending`／`PaymentConfirmed`；核定為另一條狀態。沒有稅款也不自動免申報。

匯出檔案成功只代表 `ExportPrepared`，不是申報成功。帳簿核准、官方格式前端檢查、送件與官方回執都各留證據；附件未完成也須列為例外。回執核對稅目、法人、年度／期別、申報版次、官方收件編號／收件時間與保存 hash，再由核准角色確認。繳款證明不能替代申報回執；錯期回執不能拿來完成本期。[財政部營業稅電子申報常見問題](https://www.tax.nat.gov.tw/alltax-faq.html?id=2)

更正建立新底稿與新送件版次，保留原回執及差異，依當期官方流程選媒體或人工處理。逾期、補件與 unknown 狀態交辦責任人，查詢原送件，不用新 request ID 盲目重送。首版候選是「會計師／記帳士交接＋人工依官方工具送件＋受控回執登錄」，不預設財政部提供可任意呼叫的申報 API。

## 8．電子發票、作廢、折讓與退貨

### 8.1 規格、資格與字軌

截至查核日，平台官方公告指出自 115 年 1 月 1 日全面使用 MIG 4.1；現行 Turnkey 上線前自行檢測作業為 V4.8.1，文件日期 115 年 8 月 20 日。adapter 須鎖定 MIG／XSD、Turnkey 或加值中心服務版次與對應檢核；不能拿歷史 MIG 3.x 範例當現行格式。[平台 MIG 公告](https://www.einvoice.nat.gov.tw/static/ptl/ein_upload/download/321.pdf)、[官方上線前自行檢測作業](https://www.einvoice.nat.gov.tw/static/ptl/ein_upload/download/5440.pdf)

正式候選包含自有系統＋Turnkey 或經核准加值服務中心；尚未選供應商、取得字軌、申請憑證或完成自檢。正式啟用須確認稅籍身分、電子發票資格、取號及總分支配號、自檢、買受人交付與平台存證責任。平台一般查詢 API 不能代替開立／存證介接。[電子發票實施作業要點](https://law-out.mof.gov.tw/LawContent.aspx?id=FL041411)

字軌以法人／期間／分支分配，保留取得來源、配號事件、已分配、已開立、作廢、空白及回報狀態。號碼保留與建立發票是原子操作；不能把 timeout 的號碼立即回收再開新單。跨期、重號、超核定範圍、錯法人與來源版本不符都拒絕。SIM 練習只用不可冒充正式字軌的合成識別；不得列印可兌獎樣張。

開立時序依適用的銷售憑證時限表及交易類型判斷，包含貨物、服務、分期、預收等，不能統一設為「收款成功才開票」。發票課稅別及金額是已核准銷售文件快照；付款狀態與發票狀態各自顯示。開立事實時間不能為了延期存證而改成送出時間。[營業稅法及銷售憑證時限表](https://law-out.mof.gov.tw/LawContent.aspx?id=FL006082)

### 8.2 存證期限與時鐘

官方現行時限表規定，發票開立、更正、作廢或開立退回／折讓證明單後，買受人為非營業人自翌日起算 2 日內、為營業人自翌日起算 7 日內傳輸；空白字軌及總分支配號按每二月一期、次期開始 10 日內。存證末日遇週末或休息日不予延長。不得直接套營業稅申報的假日順延規則。[財政部法規時限表](https://law-out.mof.gov.tw/EngLawContent.aspx?KW=Business+Tax&id=20714&lan=C)、[財政部賦稅署時限表附件](https://law-out.mof.gov.tw/Download.ashx?FileID=52363&id=20714&type=ANNE)

`deadlinecalc` 依 `buyer_classification`、`tax_event_date`、事件類型、法域與政策快照產生每次操作的期限；捐贈／列印變更與空白字軌回報另有排程。起算日以台灣日期、日曆日規則計算，跨 UTC 午夜不可少算或多算一天。建議在開立後立即排程傳輸與結果查核，接近期限仍未存證成功就升級給責任人；提醒不延長期限。不可抗力或不可歸責事件須保存證據並依規定申請，系統不能因服務商維修自動認定免責或延長。[官方時限表](https://law-out.mof.gov.tw/EngLawContent.aspx?KW=Business+Tax&id=20714&lan=C)

### 8.3 發票與外部操作狀態機

發票業務生命週期與傳輸生命週期分離；`Issued` 不等於 `StoredConfirmed`，HTTP 200 或服務商「受理」不等於財政部已存證。

| 物件 | 狀態與規則 |
| --- | --- |
| 開立文件 | `Draft → Validated → Approved → NumberReserved → Issued`；未開立的 draft 可取消，已開立則走獨立作廢操作 |
| 存證操作 | `Prepared → Queued → Sent → ProviderAccepted → StoredConfirmed`；另有 `Rejected`、`Unknown`、`ManualResolutionRequired` |
| 作廢 | `Requested → EvidenceReviewed → Approved → Submitted → VoidConfirmed`；原發票狀態只在確認後標作廢，保留字軌及原件 |
| 折讓 | `Draft → AgreementRecorded → Reviewed → Approved → Issued → StoredConfirmed`；折讓作廢再另建 operation，不刪折讓歷史 |
| 退貨 | 依業務驗收記錄數量／狀態與庫存事件；它不自動完成退款或折讓 |
| 退款 | 由 treasury 管理核准、準備、送出及銀行確認；付款未知不阻止保存已發生退貨事實 |

作廢用於符合規則的原票處理；開票後經雙方合意退回或折讓，須另走電子退回／折讓證明單、買受人交付及存證。不能把所有退貨都變成刪發票，也不能退款成功就自動認定稅務已調整。重開新發票、折讓額度、原明細與數量對照、跨期調整及已申報期影響均須核准。[統一發票使用辦法第 20 條之 1 與第 24 條](https://law-out.mof.gov.tw/LawContent.aspx?id=FL006084)

同意證據及相關文件列入受控留存；現行作業要點要求相關同意訊息與證明至少保存五年。以公開訪客試用的短期資料清除機制無法承擔這項責任，正式候選須另建留存、備份、權限與終止服務取回資料安排。[電子發票實施作業要點第九點](https://law-out.mof.gov.tw/LawContent.aspx?id=FL041411)

### 8.4 Unknown、重送與事件關聯

逾時、連線中斷、未驗證回應或服務商受理但平台結果未明，均標 `Unknown` 或仍等待存證。保存原 logical operation ID、冪等鍵、payload hash、字軌與 request ref；先查原操作與平台結果，再決定是否補送。不能換新 key 反覆開票，不能只因 timeout 判定失敗後重新配號。

只有 adapter 契約確認外部冪等範圍與可重試條件，才能用相同 logical operation 進行受控 retry；每次 transport attempt 有獨立 attempt ID。服務商無冪等或可靠查詢時走人工處理佇列，不宣稱 exactly-once 外部執行。

webhook／Turnkey 結果通過來源與簽章核對、外部 event ID 去重、correlation ID 與法人／文件／操作類型核對後寫事件。遲到、重複、亂序或同 key 異內容隔離；更晚收到的「受理」不能把已確認存證倒退。不同外部來源互相矛盾時保留證據並人工處理，不按最後收到的文字直接改狀態。退貨、退款、發票及總帳以可追蹤事件協調，網路結果不能在本地交易中假裝原子成功。

## 10．權限、覆核與稽核

採 maker-checker。角色在 entity 與門市／部門範圍授權，薪資與稅務私人資料另有欄位級權限。`approvals`、`documents`、`connectors` 為企業共用依賴的 Planned 模組；財務功能必須與其契約對齊後才可啟用。

| 角色／能力 | 可做 | 必須分離的權限 |
| --- | --- | --- |
| 來源制單者 | 上傳合成或獲授權來源、編 mapping、建立建議配對與費用 | 不能核准自己的匯入、差異與付款 |
| 財務覆核者 | 覆核來源、清償、對帳及差異 | 不能在核准後改 payload；過帳／銀行執行權限按責任再分 |
| 會計制單／覆核 | 科目、傳票、月結及沖回 | 同張傳票制單與覆核不能同一 actor；政策與重開亦須獨立覆核 |
| 薪資專員／薪資覆核 | 授權範圍試算與核准 | 薪資規則與最終付款分別授權；經理不能看全公司員工私有明細 |
| 稅務負責人／授權代理人 | 稅籍、底稿、交接與回執核對 | 正式送件與代理資格須另獲授權；財務制單不能冒充官方已收件 |
| 發票操作／覆核／執行器 | 開立預覽、作廢折讓審查、核准操作排程 | 執行器僅消費核准 payload；不能自行改稅別、字軌或合意證據 |
| 稽核者 | 只讀原件、版本、事件及報表快照 | 不修改原帳或核准自己的更正；敏感原件需單獨授權 |

小店可由老闆與外部記帳士分工；單一人員無獨立覆核時，系統明列「待覆核」，不虛構第二人。教學可以用合成角色演練，但不能把角色切換當正式雙人覆核。權限授予、代理資格與付款收款目的地變更也須覆核，核准者不能藉由更改目的地跳過原核准。

稽核事件記錄 actor ref、操作理由、物件版本、前後摘要 hash、核准 ref、來源與結果；私人原文與 secret 不進事件。原始帳簿、銀行來源、薪資原件、申報／發票回執分別訂留存政策與法律保留，未核定法定保存年限的類別不得自動清除。正式候選須有備份還原、時間可信度、最小權限、離職撤權與資料匯出稽核；本次沒有實施或測試這些能力。

## 12．實作順序與正式接入前的未決條件

本輪只安排設計，全專案沿用共同順序：P0 身分／權限／資料契約 → P1 組織與 HR → P2 排班與出勤 → P3 薪資 → P4 會計／採購／資產／銀行對帳 → P5 稅務與發票 → P6 正式候選 adapter。P3 可先在合成資料完成計薪與凍結結果，正式過帳依賴 P4 GL 驗收；P4 內部先完成科目、AR／AP 與來源契約，再接費用、資產、合成銀行對帳及月結。每階段先完成其驗收再向下游送事件，不能為了示範畫面先放行正式端點。

正式候選啟用前須另完成並留下證據：

1. 明確法人、實際業別、稅籍核定、會計年度、準則、稅目與正式責任人，由合格會計／稅務人員覆核適用規則。
2. 將目前 SIM 與正式環境分離；新資料庫、新 tenant 存取、schema migration、版本回復與還原驗收，不導入模擬餘額充當正式期初。
3. 取得選定銀行產品的匯入／匯出與查詢規格、來源授權、格式版次及去識別測試樣本；選定各銀行格式後才宣告相容，沒有通用銀行格式承諾。
4. 確認首階段是人工銀行證據還是授權只讀連線；付款與薪轉送出另行授權、驗證清償結果與部分成功，不共用讀取授權。
5. 建立受控私人資料與 secret 儲存、稽核遮罩、資料留存與法律保留；測試環境、公開 repo 與示範資料不可含真人 PII 或真帳戶。
6. 核定當年度保費、級距、扣繳表、法定常數、捨入、假日與延期公告；標記來源 hash／effective date／tax year，補完整保險資格與所得分類測試。
7. 識別營業稅申報格式與年度營所稅／扣繳媒體規範，完成官方工具前端檢查與會計師交接驗收；決定回執核對與更正責任，不能假設存在通用申報 API。
8. 選定電子發票自有 Turnkey 或合格加值中心，完成稅籍／憑證／字軌／配號、完整 MIG/XSD 逐欄映射、最新自檢及存證結果查核；目前未完成完整 MIG 本體逐欄驗證。
9. 確認外部提供者冪等、查詢、簽章／事件、字軌佔用、維修、退出與資料返還契約；無可靠查詢就明列人工處理，不能只靠 retry 補償。
10. 驗證雙人覆核、管理員權限、目的地變更、actor 不可冒用、稅務代理授權及離職撤權；單人小店須安排外部覆核或承認未滿足該門檻。
11. 完成備份還原、稽核紀錄完整性、月結重開與資料保全、申報／發票逾期異常責任及事件處置演練。
12. 由使用者明確授權正式環境、指定介接方式與操作範圍，再在隔離的測試／驗證環境完成端到端驗收。這份設計文件不構成正式接入、送件、開票或付款授權。
